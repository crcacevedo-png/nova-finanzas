# RCA — informe-anestesia-diario cron still not firing (2026-11-15 Guatemala)

## Problem statement
User reports that the `informe-anestesia-diario` cron (`0 18 * * *` America/Guatemala → `POST /api/cron/informe-anestesia-diario`) did NOT fire again today, Sunday 2026-11-15 (Guatemala). The sibling `cierre-diario` DID fire (totals=0, expected — clinic closed Sunday). This continues the previously escalated platform bug (RCA_ac2e75d1-… and RCA_6caae3c2-…): production cron registration never reconciled with `.emergent/crons.yml` (4 entries: respaldo-semanal, cierre-diario, informe-anestesia-diario, produccion-palma). Already escalated to Emergent support.

Three questions asked:
1. Any incoming POST to `/api/cron/informe-anestesia-diario` today (even rejected)?
2. Any incoming POST to `/api/cron/produccion-medico-diario` today (23:00 UTC / 17:00 Guatemala)?
3. Has the cron registry/scheduler been reconciled yet — are informe-anestesia-diario and produccion-palma now registered, or still only cierre-diario/respaldo-semanal?

## Investigation
- `describe_deployment_state`: active run is `050b5335` (redeploy, promoted 2026-11-16T03:47Z). A redeploy happened TODAY at 03:42 UTC Nov 16 — AFTER both cron fire times. So the pods serving during the cron window (00:00 UTC and 23:00 UTC Nov 15) belonged to the PREVIOUS run `9f57b262` (live Nov 15 00:49 → today's redeploy). Logs were therefore read from BOTH runs.
- `fetch_app_logs` on run `9f57b262`, filter `cron|informe-anestesia|produccion|cierre|respaldo`, `since_minutes=600` (window ≈ 18:30 UTC Nov 15 → 04:30 UTC Nov 16 — fully covers both 23:00 UTC Nov 15 and 00:00 UTC Nov 16 fire times). 185 matching lines returned, all under the 400-line cap (no truncation).
- `fetch_app_logs` on active run `050b5335` for the same filter — only post-redeploy internal gcal-sync lines, no external cron POSTs.

## Evidence
From run `9f57b262` (the run that was actually serving traffic during the cron window):

- The ONLY external `POST /api/cron/*` in the entire window:
  `INFO:     104.22.100.52:0 - "POST /api/cron/cierre-diario HTTP/1.1" 200 OK`
  Source IP `104.22.100.52` is a Cloudflare egress address — i.e. the platform cron scheduler. It landed at the ~00:0x UTC Nov 16 boundary (18:0x Guatemala Nov 15). This matches the user's report that cierre-diario fired.
- NO `POST /api/cron/informe-anestesia-diario` anywhere in the window — its 00:00 UTC Nov 16 fire time is covered. Not even a rejected/4xx attempt. Zero incoming request.
- NO `POST /api/cron/produccion-medico-diario` anywhere in the window — its 23:00 UTC Nov 15 fire time is covered. Zero incoming request.
- All remaining cron-matching lines are the app's OWN in-process APScheduler jobs (`start_scheduler.<locals>._sync_gcal_job` every 10 min; `cleanup_expired_tokens` every 6h). These are internal to the backend process, NOT platform cron invocations, and are irrelevant to the registration question.

## Root cause
The platform cron scheduler is STILL firing only `cierre-diario` (plus the weekly `respaldo-semanal`, which is outside this window). `informe-anestesia-diario` and `produccion-palma` / `produccion-medico-diario` are still NOT registered in the production scheduler — it has never been reconciled with `.emergent/crons.yml`. The absence of ANY incoming POST (not a 4xx, not a crash — simply no request arrived) proves this is upstream of the app: the scheduler never issued the call. This is NOT an application bug and NOT a deploy-pipeline failure — the app endpoint and auth never got a chance to run.

Answers:
1. informe-anestesia-diario: NO incoming POST (not even rejected).
2. produccion-medico-diario: NO incoming POST.
3. Registry NOT reconciled yet — only `cierre-diario` (and weekly `respaldo-semanal`) are firing. `informe-anestesia-diario` and `produccion-palma` remain unregistered. The platform-side fix has NOT been applied.

## Fix
- Platform (Emergent): This is the same unresolved platform-side cron-registration bug already escalated (RCA_ac2e75d1 / RCA_6caae3c2). The production cron scheduler must be reconciled with `.emergent/crons.yml` so all 4 entries — including `informe-anestesia-diario` and `produccion-palma` — are registered and fired. No code change and no redeploy on the app side will fix this; the deployer agent has no tool to register platform crons.
- User action: Follow up on the existing Emergent support ticket, quoting deployment `991c0db0-b2ab-461c-a2f2-25a399d3b426` and job `d705ebbc-2ba2-47db-bc02-6b3b16a69eb2`, and reference this RCA plus today's confirmation (2026-11-15 GT) that only cierre-diario fired.

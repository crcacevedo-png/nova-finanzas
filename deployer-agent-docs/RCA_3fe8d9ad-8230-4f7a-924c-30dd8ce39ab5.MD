# RCA — "el mail del control de anestesia no lo envió producción" (informe-anestesia-diario cron)

Deployment: novavision-finanzas (admin.novavision.me / novavision-finanzas.emergent.host)
Active run: 3fe8d9ad-8230-4f7a-924c-30dd8ce39ab5 (redeploy, success, completed 2026-11-12 01:14 UTC)

## Problem statement
Daily anesthesia report email, scheduled via `.emergent/crons.yml` cron `informe-anestesia-diario` at `0 18 * * *` / America/Guatemala (= 00:00 UTC), did not send today. Need production facts before any code fix.

## Root cause (PROVEN)
At today's 18:00 GT slot (= 00:00 UTC, 2026-11-12) the platform scheduler did **not** dispatch any webhook to `POST /api/cron/informe-anestesia-diario`. The cron was not yet registered in the scheduler at that time because the `informe-anestesia-diario` entry only reached production in a deploy that completed AFTER the slot.

Evidence:
- The run active at 00:00 UTC was **4d2ef23a** (active 2026-11-11 20:06 → 2026-11-12 00:29). Its logs around the 00:00 UTC window show the **sibling daily cron fired**:
  `INFO: 104.22.100.133:0 - "POST /api/cron/cierre-diario HTTP/1.1" 200 OK`
  (104.22.100.133 = Cloudflare / platform dispatcher). `cierre-diario` has the identical `0 18 * * *` schedule and uses the identical `WEBHOOK_CRON_SECRET` Bearer auth.
- In the same run's logs there is **NO** `POST /api/cron/informe-anestesia-diario` line at all — not even a 401. (The only "anestesia" hits are user-driven `/api/catalogos/igss-procedimientos?search=...anestesia...` API calls, not cron POSTs.) Absence of any inbound request = the webhook was never dispatched, i.e. the cron was not registered yet.
- Deploy timeline: the deploy running at 00:00 UTC was 4d2ef23a (built/promoted 2026-11-11 ~20:06). The next deploys completed 00:29 (ce628a64) and 01:14 (3fe8d9ad) — both AFTER the cron slot.
- The **newly deployed** source (active run 3fe8d9ad) now contains the entry — verified in eph sandbox `cat .emergent/crons.yml`: all three crons present (respaldo-semanal, cierre-diario, informe-anestesia-diario, enabled: true, endpoint `{{BASE_URL}}/api/cron/informe-anestesia-diario`).

## Ruled out
- **WEBHOOK_CRON_SECRET mismatch / 401**: ruled out. `cierre-diario` returned 200 OK at the same slot using the same secret → the secret is present, non-empty, and matches the dispatcher. `list_secrets` confirms WEBHOOK_CRON_SECRET present/non-empty on the active run.
- **Endpoint/auth code bug**: ruled out. `cron_informe_anestesia_diario` (~line 484) validates Bearer vs WEBHOOK_CRON_SECRET via hmac.compare_digest, backgrounds the work, returns 2xx — matches the platform cron contract. No code change needed.
- **Email provider failure**: nothing to rule in — the send logic never ran because the webhook was never received (no `Informe de anestesia ... enviado` nor `Error enviando informe de anestesia` log lines exist).

## Secondary finding (separate issue, NOT the cause of today's miss)
`INFORME_ANESTESIA_EMAILS` on the active prod run is **present and non-empty but does NOT match** the preview value `draherreranestesia@gmail.com,crcacevedo@gmail.com` (list_secrets matches_expected=false). Custom env keys carry forward from the previous PRODUCTION run; the preview `.env` only ADDS new keys, it never overwrites a key already set in prod. So a recipient-list change made in preview would NOT propagate to prod. When the cron does fire, it will email whatever the prod value holds — possibly an old/wrong list. The user should verify/correct this in the Secrets tab.

## Conclusion / expected behavior
- Today's miss is EXPECTED: the cron wasn't registered in production until this latest deploy. No code fix required.
- The next 18:00 GT run should fire, provided the deploy pipeline registered the new cron from the now-deployed crons.yml.
- CAVEAT: I have no tool to directly read the platform cron registry, so "now registered" is inferred from (a) cierre-diario proving the scheduler+secret work and (b) the deployed source now containing the entry. Recommend confirming after the next 18:00 GT run, or manually POSTing the endpoint with the correct Bearer token to validate end-to-end immediately.

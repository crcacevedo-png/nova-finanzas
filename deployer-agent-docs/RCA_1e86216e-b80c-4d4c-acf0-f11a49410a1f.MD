# RCA — Bug "Tipo de Compra" (igss_tipo_compra) viejo en PDF — Novavisión ERP (admin.novavision.me)

## Resumen ejecutivo
La versión de backend desplegada en PRODUCCIÓN (run activo `1e86216e`, imagen desplegada 2026-11-06, sirviendo novavision-finanzas.emergent.host / admin.novavision.me) **coincide con el comportamiento del código actual del preview** para este bug. No es una versión anterior con snapshot congelado. Las tres rutas de PDF leen `igss_tipo_compra` EN VIVO desde `db.patients` en cada generación, y la base de datos de producción **no guarda ningún snapshot** de ese campo. Por lo tanto, en el código que corre hoy en producción **no existe un mecanismo que pueda congelar un valor viejo de "Tipo de Compra"**.

## Qué se verificó (contra la fuente exacta del run activo en un sandbox + consultas a la BD de producción)

### 1. Versión desplegada = código actual (para este bug)
Inspeccioné el source pulled del run activo `1e86216e` (lo que se compiló en la imagen en producción):

- **`backend/routes/patients.py` → `export_patients_pdf` (línea 977):**
  - Lee en vivo: `patients = await db.patients.find(query, {"_id": 0}).sort("record_number", 1)...`
  - Headers de la tabla: `["Expediente","Nombre Completo","Género","Edad","Teléfono","DPI","Institución","Unidad IGSS","NOG"]` — **NO existe columna "Tipo de Compra"** (idéntico a lo que describiste del preview).
- **`frontend/src/services/api.js:292`:** el botón "Exportar PDF" de Pacientes llama a `${API_URL}/patients/export/pdf` (el endpoint reportlab del backend). **No hay generación client-side (jsPDF)**. => El PDF de la pantalla Pacientes no puede mostrar "Tipo de Compra" en absoluto.
- **`backend/routes/evaluaciones.py` (receta/evaluación, `get_evaluacion_pdf`):**
  - `paciente = await db.patients.find_one({"id": evaluacion.get("paciente_id")}, {"_id": 0})` (en vivo).
  - `_tc_raw = (paciente.get("igss_tipo_compra") or "")` — el tipo de compra se toma **directamente del documento vivo del paciente**. El snapshot guardado en la evaluación solo se usa como fallback para NOG/SPS/Código, **nunca** para tipo de compra.
- **`backend/routes/igss_nogs.py` (acreditaciones / export NOG):** `listar_pacientes_nog` y `_filas_export_nog` construyen cada fila desde `db.patients.find(...)` en vivo; `igss_tipo_compra: p.get("igss_tipo_compra","")` viene del paciente vivo.
- **`update_patient` (PUT /api/patients/{id}, línea 670):** `$set` directo; `igss_tipo_compra` es un único campo top-level. No se duplica dentro de `igss_ordenes[]` (que solo guarda `{id, nog, no_sps, codigo, procedimiento}`). No hay caché intermedia.

### 2. La BD de producción no guarda snapshot de tipo_compra
DB: `novavision-finanzas-test_database`.
- `evaluaciones_oftalmologicas`: proyección de `tipo_compra`/`igss_tipo_compra`/`igss_*` → **ningún documento contiene esos campos** (solo `paciente_id`, etc.).
- `igss_nog_acreditaciones`: igual, **no guardan `tipo_compra`** (solo `paciente_id`, `numero_nog`, ...).
- grep global `igss_tipo_compra`/`tipo_compra` en `backend/routes/`: solo aparece en patients.py, evaluaciones.py e igss_nogs.py — todos lectura en vivo.

## Respuestas a tus 3 preguntas
1. **¿Qué versión está desplegada?** La del run `1e86216e` (2026-11-06). Para `patients.py`, `evaluaciones.py` e `igss_nogs.py` su comportamiento es **igual al código actual**: sin columna "Tipo de Compra" en el PDF de Pacientes y con lectura en vivo en receta y reportes NOG. **No es una versión anterior con bug de snapshot.** (Nota: en general producción SÍ es anterior al preview — no incluye el trabajo reciente solo-preview de LIO/Pre-Ops/filtro de Mes/192 cirugías — pero esos cambios no tocan la lógica de tipo_compra de los PDFs.)
2. **Causa raíz del snapshot/caché en servidor:** **no existe** en el código ni en los datos desplegados. Ninguna ruta de PDF puede devolver un tipo_compra viejo a partir de la BD de producción.
3. **¿El fix ya existe?** Sí: la lectura en vivo ya está presente en el código desplegado. **No hay nada adicional que corregir en el backend** para este comportamiento, y re-desplegar el preview actual **no cambiaría** estas tres rutas respecto a este bug.

## Causa más probable del síntoma observado (a verificar del lado cliente/edge)
Dado que backend, datos y código están limpios, el valor "viejo" que ves proviene casi seguro de **fuera del backend**:
- **PDF de Pacientes:** no tiene columna "Tipo de Compra" en producción ni en preview. Si viste "Tipo de Compra" ahí, estás mirando un **PDF descargado antiguo** u otro artefacto, no el actual. => confirmar de qué pantalla exacta salió el PDF.
- **PDF de receta/evaluación o reporte NOG:** estos sí muestran tipo_compra (en vivo). Un valor viejo aquí apunta a **caché del navegador o del edge de Cloudflare sobre la respuesta GET del export** (el frontend es Cloudflare → R2 + proxy /api). `export_patients_pdf` retorna `StreamingResponse` solo con `Content-Disposition` (sin `Cache-Control` explícito en el código).

### Hardening opcional (NO es la causa raíz comprobada)
Si al verificar en DevTools aparece `cf-cache-status: HIT` o cache del navegador en las rutas de export, se puede añadir como mejora preventiva `Cache-Control: no-store` a las respuestas GET de export de PDF/Excel. No es necesario para corregir la lógica (que ya es correcta).

## Qué NO hacer
- No re-desplegar esperando que arregle este bug: la lógica desplegada ya lee en vivo. (El redeploy del preview actual traería otros cambios no solicitados — LIO/Pre-Ops/192 cirugías.)

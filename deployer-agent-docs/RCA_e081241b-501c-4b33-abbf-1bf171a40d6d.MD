# RCA — NovaVisión ERP: "administrador_igss" cannot create NOGs in production

## Problem statement
Role `administrador_igss` (user-reported) cannot create NOGs on IGSS units in the LIVE site (`https://novavision-finanzas.emergent.host`). Same flow returns 200 in preview. Hypotheses to verify (read-only): (a) prod role missing `manage_igss_units: true`; (b) prod running an older build predating the NOG feature/permission.

## Deployment context
- Active run: `e081241b-501c-4b33-abbf-1bf171a40d6d` (redeploy, status success, promoted 2026-10-21 14:04 UTC).
- DB read: `novavision-finanzas-test_database` (resolved server-side).
- Frontend type: cloudflare (static served from R2).

## Findings

### (a) Production role DOES have the permission — hypothesis DISPROVEN
`roles` collection, document `name: "administrador_igss"` (display_name "ADMINISTRADOR IGSS ", is_active: true). Full `permissions` object:
```
create_patients: true
delete_patients: true
edit_patients:   true
export_patients: true
manage_doctors:  true
manage_igss_units: true   <-- PRESENT and TRUE
view_patients:   true
```
`manage_igss_units` is present and set to `true`. The role is NOT missing it.

Affected users: exactly ONE user holds this role in prod — `username: sandrac` (is_active: true). (`users` filter `{role:"administrador_igss"}`, count 1.)

### (b) Deployed build IS current — hypothesis DISPROVEN
Inspected the active run's own source in an isolated sandbox (`/app/scratch`, run e081241b):
- Route exists: `backend/routes/igss_nogs.py:296` → `@router.post("/{unit_id}/nogs")`, gated by `Depends(require_permission("manage_igss_units"))` (line 300).
- Permission catalog served by `GET /api/roles`: `backend/routes/roles.py:69` includes `{"id":"manage_igss_units","label":"Gestionar Unidades IGSS",...}`.
- The NOG module (igss_nogs.py) is fully present with the modern feature set (resumen, alertas, acreditaciones, export). This build is NOT a pre-NOG build.

### Permission resolution path (confirms backend WOULD grant it)
`routes/auth.py.get_current_user` sets `user["permissions"] = await resolve_permissions(user["role"])`, and `require_permission` checks that dict. `config/permissions.py.resolve_permissions("administrador_igss")`:
- not superadmin → reads `db.roles.find_one({"name":"administrador_igss"})` → found with non-empty `permissions` → merges onto the (empty) system default and applies the stored dict, which contains `manage_igss_units: true`.
- Result: effective `manage_igss_units = true`. The backend would return 200, not 403, for this role.

Only non-permission rejection paths in the POST handler: unit not found → 404; duplicate NOG `numero` in the same unit → 400 "Ya existe un NOG con este número en la unidad".

### (4) Production logs — no 403 on NOG creation
`fetch_app_logs` (run e081241b, last 1440 min, filter `igss-units|nogs|403|permission`): many `GET .../nogs` and `GET .../nogs-activos` return 200; one `POST /api/igss-units` (unit create) returned 200. **No `POST /api/igss-units/.../nogs` request appears at all, and no 403 on any NOG route.** The only 403s in the window are on `PATCH /api/evaluaciones/.../autoguardar` (unrelated feature). So there is no backend permission-denied evidence for NOG creation in the last 24h.

## Root cause
The two proposed root causes are **both disproven**: (a) the production `administrador_igss` role already has `manage_igss_units: true`, and (b) the deployed build is current (POST `/igss-units/{unit_id}/nogs` present and gated on `manage_igss_units`; the permission catalog exposes the key). Given the role grants the permission and permissions are resolved from `db.roles` on every request, the production backend would authorize this role to create NOGs (return 200). The reported failure is therefore NOT a prod role-data gap and NOT a stale/old build. No failing POST and no 403 is present in 24h of prod logs, so the actual denial could not be observed from the server side — the failing request needs to be captured from the client to determine what is really happening (e.g., a 400 duplicate-número, a 401 revoked/stale session via `token_version`, a frontend route guard, or the request never leaving the browser).

## Suggested next step
Have `sandrac` reproduce the failure in the LIVE site with browser DevTools → Network open, and capture the `POST /api/igss-units/{unit_id}/nogs` request: HTTP status code and JSON response body. 
- 403 "No tienes permiso..." → would contradict the DB/code evidence; re-check the exact token/role on that session (log out/in to refresh JWT) and re-run this RCA.
- 400 "Ya existe un NOG con este número..." → not a permission issue; the número already exists in that unit.
- 401 "Sesión revocada..." → stale session; log out and back in.
- No request in Network / a client-side block → stale frontend bundle or a UI guard; hard-refresh / incognito.

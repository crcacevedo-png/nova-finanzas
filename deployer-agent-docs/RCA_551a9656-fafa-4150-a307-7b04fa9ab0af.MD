# RCA — NovaVisión ERP: Google Calendar auto-sync not importing (PRODUCTION)

Deployment: novavision-finanzas  (`https://novavision-finanzas.emergent.host`)
Active run: 551a9656-fafa-4150-a307-7b04fa9ab0af  (redeploy, success)
DB read: `novavision-finanzas-test_database`  (read-only)

## TL;DR — the leading hypothesis is WRONG
The in-app APScheduler **IS running in production** and the Google Calendar pull job **IS firing every 10 minutes**. The symptom is **not** a dead scheduler and **migrating to a platform cron will not fix it**. The real cause is a **code-level silent-failure in the sync logic** (`backend/routes/google_calendar.py`) that lets a degraded/empty sync be recorded as "success" and keeps advancing the Google `sync_token` + `last_sync` — so new Google events stop being imported while everything still looks healthy.

---

## What was verified (evidence)

### 1) The in-app AsyncIOScheduler runs in prod — CONFIRMED
- Boot logs (run 551a9656): `INFO:apscheduler.scheduler:Scheduler started` and `INFO:server:Scheduler iniciado (gastos fijos: 00:05 diario, limpieza tokens: cada 6h, Google Calendar: cada 10min)`.
- The job fires on schedule: `INFO:server:Google Calendar sync: {'configured': True, 'medicos_sincronizados': 3, 'importadas': 0, ...}` logged ~57× in 24h ≈ every 10 min.
- The production process is a **single uvicorn worker** — `entrypoint.sh` runs `uvicorn server:app --host 0.0.0.0 --port 8001` (no `--workers`, no gunicorn, no process manager). One event loop → AsyncIOScheduler runs normally and is not killed. **There is no multi-worker setup that would suppress it.**

### 2) Config / secrets — CONFIRMED present
- `configured: True` in every sync log line → `run_sync_all` sees `GOOGLE_CLIENT_ID` + `GOOGLE_CLIENT_SECRET`.
- `list_secrets` (active run): `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_OAUTH_REDIRECT_URI` all present and non-empty. (`matches_expected:false` only because I passed empty comparison values — ignore; presence is what matters and `configured:True` proves they load at runtime.)

### 3) The pull executes and updates state — CONFIRMED
- `doctors.google_calendar.last_sync` for all 3 connected doctors = `2026-10-27T15:50:00Z` (current, advancing every 10 min). `sync_token` is populated and rotating.

### 4) ...yet nothing new is imported — CONFIRMED (the real symptom)
- Latest `citas` with `origen_google:true` was created **2026-10-24T13:50:00Z**. **No Google-origin appointment has been imported for ~3 days**, even though the job keeps running and reporting `importadas:0` success.
- Logs show Google throttling: `WARNING:googleapiclient.http:Encountered 403 Forbidden with reason "rateLimitExceeded"`.

## Root cause (code logic in `backend/routes/google_calendar.py`)

The sync is designed so that transient/API errors are swallowed and run state is advanced anyway, which permanently skips the affected change window:

1. **`_sync_doctor()` (~L339):**
   ```python
   try:
       events, next_sync = await _collect(sync_token)     # incremental
   except Exception:
       events, next_sync = await _collect(None)           # full resync, timeMin=TODAY only
   ...
   if next_sync:
       update sync_token = next_sync, last_sync = now
   ```
   - A broad `except Exception` treats **any** failure (the observed `403 rateLimitExceeded`, a token hiccup, or a mid-paging page failure) as a reason to do a full resync — and a partial/degraded read still yields a `next_sync`, which is then **unconditionally persisted**. A window that actually failed to read changes is recorded as success, the token advances past it, and those events are **never re-read**.
   - `last_sync` therefore updates even when nothing was truly synced — so "last_sync looks fresh" is misleading and must not be read as proof of healthy sync.
   - The fallback `_collect(None)` only lists `timeMin = today 00:00` (Guatemala). Any create/edit affecting an event **before today** is skipped after a token reset.

2. **`run_sync_all()` (~L537):** wraps `_sync_doctor` in `try/except` that only `print("sync_doctor error:", ...)` and still returns `configured:True` success totals — so per-doctor failures never surface.

3. **`_get_service()` (~L76) token refresh** and **`push_cita()` (~L175)** also swallow errors (`except Exception: print(...)`), so an `invalid_grant`/`RefreshError` on refresh would degrade silently too. (Not the active cause here — service calls are succeeding since `last_sync` advances — but it's the same anti-pattern and worth hardening.)

Net effect: the scheduler and API wiring are healthy, but the pull silently stops importing after the first throttled/failed window and never recovers because the token keeps moving forward.

---

## Recommended fixes

### A. Code (E1) — in `backend/routes/google_calendar.py`
- Only fall back to full resync on a **genuine 410 / invalid syncToken** (inspect `googleapiclient.errors.HttpError.status_code` / reason), not on any exception.
- Add **retry with backoff** for `403 rateLimitExceeded` (and 5xx) instead of silently degrading.
- **Do not advance `sync_token`/`last_sync` unless the read genuinely succeeded end-to-end** (collect all pages without error). On error, keep the old token so the window is retried next cycle.
- Don't clamp the resync fallback to `timeMin=today` if the goal is to catch edits to earlier events (widen the window or key off `updatedMin`).
- Surface per-doctor errors in the `run_sync_all` result and log refresh failures (`invalid_grant`) explicitly so this can't silently rot again.
- (Reproduce only partially possible in sandbox — the eph pod has the source but no live Google creds, so the 403/token path cannot be exercised there; logic reviewed statically.)

### B. One-time recovery (data / user action)
- The last ~3 days of Google-created/edited events were skipped. To recover them, **reset `google_calendar.sync_token = None` for the 3 connected doctors** so the next sync does a clean full read, then run the manual `POST /api/google-calendar/sync`. This can be done via the existing superadmin "select calendar" flow (`POST /api/google-calendar/select-calendar` sets `sync_token=None`) or a direct DB edit. Pair this with fix A, otherwise the same throttle can re-poison the token.

### Do NOT
- Do **not** migrate the job to a platform cron to "make the scheduler run" — it already runs. A cron would hit the same `_sync_doctor` logic and fail the same way. (A cron is only worth considering later for isolation/observability, not as the fix for this symptom.)

- `optica` (Usuario Óptica)
- `dianadlc` (Diana de la Cruz)
- `diana` (Diana de la Cruz)

**Ninguno tiene campo `permissions` propio** en su documento de `users`. Los permisos se resuelven desde el rol en login vía `resolve_permissions(role)`.

### 2) db.roles para 'optica'

`resolve_permissions('optica')` fusiona PERMISSIONS['optica'] (estático) + este doc → resuelve **view_optica = true**. Por tanto `hasPermission('view_optica')` = true en el frontend.

### 3) db.menu_configurations para 'optica'

→ **Ya incluye `optica_pos` y `optica_cxc`.** (También incluye `finanzas_pos/finanzas_caja/finanzas_cxc`, pero ver abajo: son INERTES para el rol óptica.)

### 4) GET /api/menu-config/my-menus
El endpoint devuelve `menu_ids` = el `enabled_menus` del doc de arriba (todos esos IDs existen en AVAILABLE_MENUS, ninguno se descarta). Por tanto `menu_ids` para óptica incluye `optica_pos` y `optica_cxc`.

## Conclusión / Causa raíz

**Descartada la hipótesis de "rol personalizado → menú vacío []".** NO aplica aquí: todos los usuarios de óptica usan el rol de SISTEMA `optica` y SÍ existe doc en `menu_configurations` para ese rol. No se necesita el fix de código para que roles personalizados hereden un default en este síntoma.

Se separan dos ítems distintos:

### A) POS óptica (`optica_pos`) y Cuentas por Cobrar óptica (`optica_cxc`)
Gobernados por "Menús por Rol" (menu_configurations). **El estado ACTUAL ya es correcto**: el doc de óptica incluye ambos, el rol tiene `view_optica=true`, y en `Layout.js` ambos se renderizan si `canViewOptica && isMenuEnabled(...)` (líneas 215–219). Los menús se cargan en el `useEffect([user])` de AuthContext (al iniciar sesión). La edición del doc (15:24) es posterior a la queja original → el origen fue una config de "Menús por Rol" para el rol óptica que NO incluía esos IDs; **ya fue corregida por config**. Si el usuario aún no los ve, es porque no ha vuelto a iniciar sesión / tiene bundle en caché (menús se recargan solo al cambiar `user`).

### B) "Caja" — NO es corregible por configuración
En `frontend/src/components/Layout.js` línea 135 el bloque de Finanzas (que contiene Punto de Venta, **Caja** y CxC clínica) está **excluido por código para el rol óptica**:
```
if (user?.role !== 'optica') { ... finanzas_caja → '/caja' ... }
```
Además NO existe ningún ítem/ruta de "Caja" específico de óptica (ni en default ni accesible para el rol). Por eso agregar `finanzas_caja`/`finanzas_pos`/`finanzas_cxc` al menu_configurations de óptica **no tiene efecto** — esos IDs quedan inertes porque el bloque nunca se evalúa para óptica. Si el cliente quiere que óptica acceda a Caja, requiere **cambio de código** (E1): añadir un ítem de Caja visible para óptica + su ruta, o relajar el guard de rol.

## Evidencia
- users: 3 usuarios role=`optica`, sin `permissions` propio.
- roles: doc `optica` con view_optica=true, manage_optica_sales=true, manage_caja=true.
- menu_configurations: doc `optica` con optica_pos + optica_cxc presentes.
- menu_config.py `/my-menus`: devuelve menu_ids = enabled_menus (todos válidos en AVAILABLE_MENUS).
- Layout.js:135 guard `user?.role !== 'optica'` excluye Finanzas/Caja para óptica.
- AuthContext.js: isMenuEnabled usa menu_ids; permisos vía resolve_permissions.

## Nota (bug latente, NO causa actual)
`DEFAULT_MENU_CONFIG.get(role, [])` devuelve [] para roles personalizados sin doc en menu_configurations. Hoy no afecta porque óptica es rol de sistema con doc propio, pero si en el futuro crean un rol óptica personalizado sin su doc de "Menús por Rol", el menú saldría vacío. Mitigación opcional (código): fallback a un default no vacío para roles sin config.

## PART 1 — Production memory at ~86% ("Critical")

### What I could verify with tools
- **No crash / no OOM:** `get_pod_events` shows the pod `r-6caae3c2-...-m8cgw` Running since 2026-11-14T02:28:16Z, `restart_count: 0`, no `OOMKilled`, no kill_findings over the last 24h. A true runaway leak sitting at 86% with zero users would eventually cross 512Mi and OOMKill/restart — it has not in ~22h.
- **Tier ceiling (`get_tier`):** tier_0 Starter = memory request 200Mi, **memory limit 512Mi**, 2 replicas, HPA/VPA disabled. 86% is measured against the 512Mi limit ≈ ~440Mi RSS/replica.
- **Architecture:** MongoDB is **external (Atlas via MONGO_URL)** — there is NO co-located mongo process in the pod. frontend is served from Cloudflare/R2. So the pod's memory is essentially the single uvicorn/Python backend process; there is no python-vs-mongo-vs-other split to report — it's ~100% the backend process.

### Source inspection (eph sandbox, run source at /app/scratch)
The in-memory structures the user hypothesized were checked directly:
- **`blacklisted_tokens = set()`** (config/database.py:24) is **DEAD/vestigial code.** It is imported in routes/auth.py but never `.add()`-ed anywhere. The real token blacklist is **persistent in MongoDB** (`db.token_blacklist`, with a TTL index `blacklist_ttl` expireAfterSeconds=0 — server.py:4601-4628). So this is NOT a growing in-memory set.
- **`query_cache = SimpleCache(default_ttl=30)`** (server.py:120-150): TTL-bounded, 30s, with eviction on get and `invalidate()`. Not unbounded.
- **`_perm_cache`** (config/permissions.py:241): keyed by role name — bounded by the number of roles. Not unbounded.
- **WebSocket `ConnectionManager.active_connections`** (server.py:155+): sets keyed per channel — scales with LIVE connected clients. With 0 active users it is effectively empty, so it cannot explain a standing 86%.
- **httpx clients** (fel.py, email_service.py): all use `async with httpx.AsyncClient(...)` — properly closed, no connection/client leak.
- **Heavy deps are installed but NOT imported at runtime:** `numpy, pandas, onnxruntime, litellm, openai, google-genai/generativeai, huggingface_hub, tiktoken, tokenizers, locust, pymupdf, emergentintegrations` return **0** import references in runtime code (routes/services/server). They inflate the image but do NOT contribute to RSS. What actually loads at startup is fastapi/starlette/uvicorn, motor, apscheduler, pydantic, bcrypt/jwt, slowapi, boto3, and **reportlab** (module-level in routes/evaluaciones.py).
- **Scheduler:** 3 recurring jobs — fixed-expenses (daily 00:05), cleanup_expired_tokens (every 6h), **google_calendar_sync (every 10 min)**. The 10-min sync is the only continuous background churn; its httpx usage is context-managed.

### Diagnosis: most likely HIGH FIXED BASELINE on a small tier, NOT a classic unbounded leak
No unbounded in-memory accumulator exists in the code, and there has been no OOM/restart in 24h — both argue against a runaway leak. ~440Mi against a 512Mi tier-0 limit is a tight baseline; Python does not return freed memory to the OS, so RSS ramps after deploy and plateaus near the top, which reads on the monitoring panel as a line "climbing then pinning" at ~86%. The 75% "Critical" threshold is simply low relative to this app's baseline on the smallest tier.

### IMPORTANT honesty / limits of this investigation
I **cannot directly measure** production per-process RSS or the multi-day / multi-deploy memory trend — there is no tool to exec into the production pod or read historical memory metrics, and the eph sandbox runs with different (larger) resources and no live state, so it cannot reproduce production memory. I therefore could not 100% distinguish "benign plateau" from "slow leak that simply hasn't crossed 512Mi yet" purely from tools. The evidence (no unbounded structure, no OOM/restart) favors baseline, but the definitive test is the restart-and-observe below.
